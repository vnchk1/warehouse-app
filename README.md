# Складской учёт (Warehouse Accounting)

Приложение для учёта материалов, единиц измерения, поставщиков и поступлений на склад.

## Стек
Python 3.12, FastAPI, SQLAlchemy 2.0, Alembic, PostgreSQL 16, Pydantic.

## Описание API
| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/health` | Проверка работоспособности сервиса |
| `POST` | `/api/units/` | Создать единицу измерения |
| `GET` | `/api/units/` | Список единиц измерения |
| `POST` | `/api/materials/` | Создать материал |
| `GET` | `/api/materials/` | Список материалов (с пагинацией `?skip=&limit=`) |
| `POST` | `/api/suppliers/` | Создать поставщика |
| `GET` | `/api/suppliers/` | Список поставщиков |
| `POST` | `/api/receipts/` | Оформить поступление |
| `GET` | `/api/receipts/` | Список поступлений (фильтры: `?material_id=&supplier_id=`) |
| `GET` | `/api/reports/summary` | Сводный отчёт по количеству поступлений |

## Схема данных
- `units` (Единицы измерения): `id`, `name` (unique), `created_at`
- `materials` (Материалы): `id`, `article` (unique), `name`, `unit_id` (FK → units), `description`, `created_at`
- `suppliers` (Поставщики): `id`, `name`, `inn` (unique, 10 или 12 цифр), `phone`, `email`, `created_at`
- `receipts` (Поступления): `id`, `document_number` (unique), `material_id` (FK → materials), `supplier_id` (FK → suppliers), `quantity` (>0), `received_at`, `created_at`

**Связи:** 
`units` 1──N `materials` 1──N `receipts`
`suppliers` 1──N `receipts`

## Правила внесения изменений (Git Workflow)

### Обязательные команды локальной проверки
Перед созданием коммита или запроса на слияние необходимо выполнить:
- `make quality` (форматирование и статический анализ через ruff)
- `make test` (автоматические тесты)
- `make verify` (полный набор локальных проверок)

### Порядок внесения изменений
1. Изменение начинается с задачи (Issue).
2. Создается отдельная ветка от `main` (формат: `feature/<описание>` или `fix/<описание>`).
3. Вносятся изменения с осмысленными коммитами.
4. Выполняются локальные проверки (`make verify`).
5. Создается Pull Request (Merge Request) в ветку `main`.
6. Изменения критических файлов (модели, миграции, конфиги) проверяются отдельно.
7. После одобрения изменения сливаются в `main`.

### Запрещенные действия
- Удалять тесты, отключать анализаторы или снижать пороги качества ради прохождения проверки.
- Ослаблять CI-конвейер.
- Коммитить файлы `.env`, `.venv/`, `__pycache__/` и другие артефакты, указанные в `.gitignore`.
- Прямые пуши (push) в ветку `main` в обход Pull Request.

### Порядок приемки
1. Все автоматические проверки (CI) завершены успешно.
2. Код прошел ревью (изменения критических файлов проверены отдельно).
3. Изменение протестировано локально (включая проверку через `make run` и API-запросы).
4. История коммитов в PR осмысленна и соответствует стандарту Conventional Commits.
